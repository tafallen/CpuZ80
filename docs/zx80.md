# ZX80 machine — architecture and design decisions

This document describes how the Sinclair ZX80 is emulated in `Machines.Zx80`, what
hardware mechanisms are in play, and the design choices made during implementation.

---

## Hardware overview

The ZX80 (1980) is a minimal Z80-based home computer:

- **CPU**: Z80 at 3.25 MHz
- **ROM**: 4K at `0x0000–0x0FFF` — BASIC interpreter + OS (8K on ZX81)
- **RAM**: 1K at `0x4000–0x43FF` — system variables, display file, BASIC program
- **No dedicated video or I/O chip** — display and keyboard handled by TTL discrete logic
- **Display**: 32×24 characters, 256×192 pixels, black and white only
- **Keyboard**: 8×5 matrix, active low
- **Tape**: single-bit serial I/O, pulse-count encoding

---

## Address map

The ZX80 uses A14-based partial address decoding (not a full 16-bit decode).
The emulator maps only the primary ranges; mirrors are not implemented.

```
0x0000–0x0FFF  ROM  (4K)
               mirrors at 0x2000, 0x8000, 0xA000 (not mapped in emulator)
0x4000–0x43FF  RAM  (1K)
               mirrors throughout 0x4000–0x7FFF and 0xC000–0xFFFF (not mapped)
0x4400–0xFFFF  unmapped → 0xFF
```

## Reset state

| Register | Value  | Reason |
|----------|--------|--------|
| PC       | 0x0000 | Z80 always starts at address 0 |
| SP       | 0xFFFF | ROM convention |
| IFF1/IFF2| false  | Interrupts disabled on reset |
| I        | **0x0E** | Required — character generator reads font from ROM 0x0E00+ |

The `I` register is critical: the ZX80 ROM sets it to `0x0E` so that the CPU's memory
refresh addressing (IR register pair) generates addresses in the font table at `0x0E00`.
`Zx80Machine.Reset()` always sets `I = 0x0E` after calling `Cpu.Reset()`.

## Display system

### Character font

The ROM contains 64 characters × 8 bytes/char at `0x0E00–0x0FFF`.
Each byte is one pixel row, MSB = leftmost pixel.

Character code interpretation:
- Bits 0–5: character index (0–63)
- Bit 7: if set, pixels are **inverted** (swap ink and paper)
- Bit 6: unused for display purposes

Ink = black (`0xFF000000`), paper = white (`0xFFFFFFFF`).

### Display file format

The display file is a variable-length region in RAM, pointed to by `D_FILE` (0x400C):

```
Byte 0:     HALT (0x76)                 — display file start marker
Row 0:      [0–32 char codes] HALT      — character codes for row 0, terminated by HALT
Row 1:      [0–32 char codes] HALT
...
Row 23:     [0–32 char codes] HALT
```

- Minimum size: 25 bytes (all rows empty — just the 25 HALT bytes)
- Maximum size: 793 bytes (25 HALTs + 768 character bytes)
- Short rows are padded with space (char code 0x00) by the renderer

### How the real hardware generates video

The ZX80 display is generated by an unusual mechanism — the CPU literally executes the
display file as Z80 instructions:

1. The ROM display routine jumps to the display file address in the high phantom copy
   (≥ 0x8000). Character codes happen to be valid Z80 NOP-family opcodes at those
   addresses.
2. The hardware intercepts M1 (opcode fetch) cycles from addresses ≥ 0x8000 and returns
   `0x00` (NOP) to the CPU, while simultaneously latching the real character code for the
   video shift register.
3. When the CPU fetches `HALT` (0x76) — the row terminator — the hardware lets the real
   byte through, so the CPU executes a genuine HALT instruction.
4. While HALTed, the R register keeps incrementing. When R bit 6 falls from 1→0, the
   hardware fires an NMI.
5. The NMI handler advances to the next display row and jumps back to the display file.
6. After 24 rows, the ROM exits the display routine and returns to BASIC.

### How the emulator generates video

The emulator does **not** need to replicate the M1 interception mechanism. Instead:

- **`RunFrame()`** drives the CPU for one frame's worth of T-states (64,167). After each
  `Step()`, if the CPU is halted AND `Cpu.PC >= 0x8000` AND R bit 6 has just fallen
  (1→0), `TriggerNmi()` is called. This replicates the hardware timing signal.
- **`RenderFrame(IVideoSink)`** is a pure software scan of the display file in RAM —
  completely decoupled from CPU execution. It walks the display file, looks up font bytes,
  and emits ARGB32 pixels.

### Design decision: font bytes read directly from ROM array

`RenderFrame()` reads font data from a `byte[]` field (`_romBytes`) stored on
`Zx80Machine` at construction time — **not** through the `AddressDecoder` bus.

**Why**: the renderer is a pure data scan with no side effects. Reading through the bus
would couple the render path to the bus layout and could in theory trigger bus side effects.
Holding a direct reference to the ROM bytes is explicit, fast, and makes the renderer
self-contained.

The `_romBytes` field is populated by taking a copy of the ROM array before passing it
to `new Rom(rom)` in the constructor.

## Keyboard

8 half-rows × 5 keys, active low. The full 16-bit port address is used:
- **Low byte**: `0xFE` (not decoded; any even port works on real hardware)
- **High byte**: each bit selects a half-row (0 = row active, 1 = row inactive)

| Address line | High byte | Bit 0  | Bit 1  | Bit 2 | Bit 3 | Bit 4 |
|---|---|---|---|---|---|---|
| A8  | 0xFE | Shift  | Z      | X     | C     | V     |
| A9  | 0xFD | A      | S      | D     | F     | G     |
| A10 | 0xFB | Q      | W      | E     | R     | T     |
| A11 | 0xF7 | 1      | 2      | 3     | 4     | 5     |
| A12 | 0xEF | 0      | 9      | 8     | 7     | 6     |
| A13 | 0xDF | P      | O      | I     | U     | Y     |
| A14 | 0xBF | NEWLINE| L      | K     | J     | H     |
| A15 | 0x7F | Space  | Period | M     | N     | B     |

Notes:
- No Symbol Shift (that is a ZX Spectrum addition).
- NEWLINE maps to `PhysicalKey.Return`.
- Multiple rows may be selected simultaneously (multi-key detection via AND).

## Tape

Format: `.o` / `.80` (not `.p` — that is ZX81).

- **No header, no filename** — file is a raw RAM dump starting at 0x4000.
- Load length = E_LINE (0x400A, little-endian) − 0x4000.
- **EAR input**: `IN 0xFE` bit 6 — 0 = pulse present, 1 = silence.
- **MIC output**: `OUT 0xFE` bit 3.
- **Encoding**: pulse-count, MSB-first per byte.
  - 0 bit = 4 pulses (each 150 µs HIGH + 150 µs LOW)
  - 1 bit = 9 pulses (each 150 µs HIGH + 150 µs LOW)
- No leader tone — ROM samples data directly.
- ~307 baud average transfer rate.
